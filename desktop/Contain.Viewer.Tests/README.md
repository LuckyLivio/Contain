# Native desktop verification

Beta 7 adds five mandatory configuration checks in
`FirstUseConfigurationChecks.cs`, with `first-use-configuration-summary.json`.
They exercise the frozen production forms using isolated missing/invalid scopes,
personal-library conflicts, synthetic permission failures and advanced settings.
The empty-library/no-implicit-creation checks are separate from the live capture.
Native helper regressions distinguish a label's displayed HWND text from its
stable accessibility name and verify real enabled/disabled click delivery.
Disabled controls use child hit testing that includes disabled children while
still rejecting covering siblings; enabled-control obstruction checks remain
strict. These helper checks run before any live capture.

The existing optional one-capture `InstallVerification` plan now starts from the
actual packaged EXE's main **新建安装记录** button. Real keyboard input operates
the initial EXE picker (including cancel) and the existing-folder picker. Cancel
must preserve the exact previously selected record and event explanation. Missing
scope disables Start; invalidated scope and a personal-database scope conflict
must fail before session or installer creation and allow folder correction.
The ordinary flow opens no advanced settings, changes no database path and never
presses **检查环境**. After the explicit Start, duplicate clicks and the main task
entry cannot start another task. The persisted scope is compared to the exact
native-picker path, and the suggested EXE filename must be the saved name.

This live scenario seeds three synthetic historical controls to retain the old
same-name/exact-UUID association checks; `first_use.preexisting_session_count`
states that distinction from an empty first-ever library. The one controlled
fixture obtains its separately prepared installation target from the guarded
fixture-only `CONTAIN_FIXTURE_ROOT`; no installer parameters are entered through
advanced settings. Process/file ETW must be active, registry observation must
remain `not_requested`, and the existing independent High file-event oracle,
explain, export and cold restart checks remain mandatory.

`install-summary.json.first_use` binds these actions, interaction counts, scope
hashes, exact session and native Windows/DPI to the frozen package.
`install-progress.json` retains only safe stage names, error types and counts.
`install-first-use-configured.png` and `install-first-use-missing-folder.png`
capture the actual owned InstallForm window, resolved from its control HWND;
they do not accidentally capture its main owner. Real DPI is recorded separately
from the existing 150%/200% simulated layout checks. No extra successful capture
or retry is introduced for layout or failure-path verification.

Beta 6 adds eight required search-export checks in `SearchExportVerification.cs`.
The actual packaged EXE searches the same 53-match fixture, selects event 120
on page two, invokes its export action and operates the native SaveFileDialog.
The actual HTML in `reports/search-export-synthetic.html` is parsed and every
event-row ID is compared with the fixed ordered 070–122 oracle. Page two,
selected explanation and clipboard identity must survive export and native
dialog cancellation. Ordinary page export after clearing search is also exercised.
Failure, existing targets, equal-count replacement, escaped special text and
bounded output use isolated fixtures. `export-summary.json` and the actual report
bytes are mandatory inputs to package verification, which independently checks
the report hash and complete ordered ID list. No new installation capture runs.
`export-progress.json` is updated at each check and native save-dialog stage;
it contains only fixed stage names, control classes/IDs, counts and error types.
Native Save/Cancel uses verified mouse input so no synchronous UIA Invoke remains
inside the modal dialog. The filename is entered through the focused native edit
using literal keyboard input, committed by leaving the field, and read back
before Save. Post-save evidence records only success/cancelled/failed/pending,
known error categories, and target-path equality/existence booleans; final
cancellation, failure or an unexpected output path fails immediately.
The saved-record export plan has opt-in bounded cleanup
of its own launched viewer if normal close fails; it never terminates a process
tree, and live installer verification does not opt into that cleanup.

Beta 5 adds nine required saved-record search checks in `SearchVerification.cs`.
`search-summary.json` binds the exact source and frozen package to the native
Windows version/DPI, query results and original event/explain/clipboard IDs.
The production-generated `search.db` has two same-name sessions of 130 events;
only positions 70–122 contain `Needle`, and all timestamps tie. The independent
expected IDs are fixed by these input positions, never generated by matching.
The actual packaged EXE is operated through UI Automation and must show exactly
50 then 3 ordered IDs from the selected session, explain/copy event 120, and exit
normally. The production form checks literal Chinese/space/percent/underscore
queries, operation and confidence labels, no matches, clear, query failure,
report exclusion and superseded reads. An actual schema-v3 store without modern
event documents exercises the read-only compatibility path. Original and viewed
DB byte hashes must remain unchanged; the real personal library is never used.
This plan starts no installer and no ETW capture. The ordinary current-page report,
overview, cold restart and other existing gates still run.

Beta 4 adds ten predeclared overview checks in `OverviewVerification.cs`, with
`overview-summary.json` binding the source, frozen package, UI, launcher and CLI.
Guarded copies of the existing synthetic sample exercise exit 0 with Degraded,
exit 1603 with saved completed evidence, and an unfinished record with a long
source error. The Windows built-in SQLite library changes only these marked test
copies; production databases and the real personal library are never used.
Exact category counts, unavailable versus zero, same names with different UUIDs,
external versus personal databases sharing a UUID, failed-query clearing, and all
three detail actions are checked. The actual packaged EXE supplies the three
overview screenshots and cold-restarts from another working directory to open
the same session and event. Expand/collapse, actual resize, clipboard and native
DPI observations are distinct from the existing simulated 150%/200% layout plan.
This read-only plan starts no installer or ETW session. A bounded preflight is
`Contain.Viewer.Tests.exe --overview-checks-only <package> <fixtures> <output>`;
release acceptance still requires the source-qualified complete harness.

The ordinary harness also runs eight deterministic native progress checks before
layout verification or the optional live install plan. They use the production
`InstallClient` and `InstallForm` with a clearly marked synthetic child mode in
the test executable: repeated/slow finalizing, coalesced and stale messages,
wrong session/database, concurrent stdout/stderr larger than a pipe buffer,
structured failure, missing terminal results, nonzero collector exit, missing
measurements, duplicate clicks, conservative close, details/clipboard and disposed
callbacks. Synthetic child output is never reported as installer or ETW evidence.
The child-mode environment flag exists only in this test assembly; the package
does not include it. `progress-summary.json` records the predeclared checks and
actual DPI, source and package identities. Full failure logs use private output.

For the bounded progress-only plan (no ETW/provider probe or installer launch):

```powershell
./target/viewer-tests/Contain.Viewer.Tests.exe --progress-checks-only target/beta2/progress-checks
```

That standalone mode reports `working-tree` and no package manifest identity;
release acceptance uses the full frozen-package harness and its exact source SHA.

This is a Windows integration executable, not a mock frontend. It references the
production viewer, verifies its assembly is byte-identical to the frozen package,
uses the packaged `contain.exe`, and launches the packaged desktop executable.
The normal workflow uses actual WinForms buttons, grid selection, paging, filters,
clipboard and report export. Injected file-dialog answers only replace the human's
path selection; they do not replace CLI calls, database reads, rendering or export.

From the repository root on Windows, after preparing the desktop package and
production-generated synthetic databases:

```powershell
dotnet publish desktop/Contain.Viewer.Tests/Contain.Viewer.Tests.csproj -c Release -r win-x64 --self-contained true -o target/viewer-tests
./target/viewer-tests/Contain.Viewer.Tests.exe --package target/windows-viewer --fixtures target/viewer-fixtures --output target/viewer-public --private-output target/viewer-private --source (git rev-parse HEAD)
```

The fixture directory must contain the production-generated `finished.db`,
`historical.db`, `interrupted.db` and `empty.db`, plus explicitly adverse
`corrupt.db`, `future.db` and `unrelated.db` inputs. The frozen package supplies
`samples/viewer-demo.db`. Tests copy inputs into a new, clearly named synthetic
Windows directory with spaces, Chinese and parameter-special characters. Existing
files are never overwritten. Database byte hashes are checked after viewing and
export. The default read-only plan invokes no collection, installer, provider
probe or cleanup. The explicitly selected install plan below is separate.

`Program.cs` declares the complete required check list before execution. Failed
checks remain failed; unavailable prerequisites are `not_run`. Assertion failures
have safe fixed reasons in `summary.json`; full errors stay in the private output.
The standalone harness's `--version` mode deliberately reports an incompatible
version solely to test rejection by the real process bridge. It never supplies
successful query results.

Screenshots come from the actual production WinForms controls rendered on Windows
with `DrawToBitmap` after the tested operations. They contain only synthetic model
data and the fixed reviewed synthetic path. They are not browser previews or
real-ETW captures. The actual local synthetic HTML export is copied byte-for-byte
to `reports/` only after checking its public content and identity. Linux cross-build
success cannot satisfy any native execution check.

The optional `--install-fixture <frozen-package>/contain-test-installer.exe` adds
`InstallVerification.cs`'s six predeclared checks after every original read-only
check passes. It first checks the production argument builder and status parser,
including literal quotes/Chinese/special characters, missing results, unknown
states, changed identities, nonzero collector exits and installer-exit versus
final-save boundaries. A snapshot-only invalid-EXE fault injection and read-only
database attempt then exercise the actual Start handler. They cannot receive
real ETW credit. The invalid-EXE attempt's saved unfinished session is opened by
its exact backend ID and earlier finished/unfinished records are checked unchanged.

Only then does the harness click the real production **开始记录** button for one
controlled fixture installation. It verifies duplicate and window-close guards,
actual running state, source stop/final persistence, exact auto-selected session
among older and same-name records, a real High file event matched against the
fixture's independent PID/creation-time/path/operation/time journal, production
explain, and actual local report export. No script collects the successful record
before the UI runs. `CONTAIN_FIXTURE_TRUTH` points outside the selected root;
both are new direct TEMP children named `contain-demo-*`. CI uses a fixed reviewed
TEMP and package path, with spaces, Chinese and special characters. The complete
database, oracle and full CLI exports stay private. A real export containing a
host registry SID stays local; its hash still proves the product export result.

Actual OS picker cancel and navigation have a separate bounded keyboard scenario:
the harness waits for the real native dialog, sends Escape, then reopens it,
navigates its address bar to the package directory and selects the EXE. A missing
interactive desktop is `not_run`; an attempted interaction failure is preserved
as `failed`, with no retry. Directly filling configuration fields is never counted
as native picker navigation. If unavailable, the minimum manual handoff is to open
**新建安装记录**, open the installer picker, cancel once, reopen it, navigate to a
folder containing spaces/Chinese/special characters, select the controlled EXE,
then confirm the exact displayed path. This manual handoff is not a passed test.

`install-summary.json` separates the six product checks, synthetic fault injection,
OS picker result, exact source/binary hashes, task/session/process identity,
source event and measured loss counters. `install-*.png` are the actual production
form's configuration, running, result and explain states for this UI-started
capture. No automatic retry, third-party installer, service mutation, scale test
or 32-run protocol is part of this plan. The package can identify verified product
automation while leaving the graphical milestone open for an unexecuted or failed
native picker scenario.

## Beta 6 complete search export

`SearchExportVerification` adds eight mandatory checks and writes
`export-summary.json`. It starts the frozen `Contain.Viewer.exe`, searches the
130-event synthetic session, selects event120 on result page two, and operates
the real native SaveFileDialog. It reads the actual HTML and compares every
`data-event-id` row against the independent fixed sequence070..122 (53 rows).
The selected page, copied ID and explanation must survive export and native
save cancellation. Clearing search then exports the original ordinary page.

The byte-unchanged `reports/search-export-synthetic.html` is the public acceptance
example. It contains synthetic names/resources only; private database paths and
harness directories are rejected before publication. Screenshots use the actual
Copy ID action to clear the completed report's private destination from status.
No installer or ETW capture is added.

Production-control regressions cover no matches, pending/failed queries, no row
selected, existing targets, a filesystem commit failure, equal-count replacement
of a first-page event, and cancellation. A separate formatter regression cancels
after writes begin and refuses escaped HTML above64MiB. Special-character data
round-trips through literal search and HTML escaping. Original fixtures and the
restored isolated personal library must remain byte-identical; no operation-owned
temporary report may remain.
